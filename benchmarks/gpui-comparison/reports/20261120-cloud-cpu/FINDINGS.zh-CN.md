# zgpui 与 GPUI：首轮 CPU 对照实测

**首轮尚未达到“全面超越”。** 在同一固定几何任务里，zgpui 的新建布局和改尺寸路径更快；GPUI 在较大场景的保留布局和部分几何查询中更快。这是同一云端 CPU 上的核心布局对照，不能外推为完整桌面框架或 GPU 渲染胜负。[完整表格](report.md)保留每组的 p50、p95、p99、配对均值区间与分配统计。

## 问题与可比范围

测试的问题是：两种实现生成相同的叶节点矩形时，构建、重复布局、改尺寸和简单几何查询分别需要多少工作？场景含 1、16、64、225 个叶节点，对应 3、21、73、241 个总节点。每个叶节点高 24 像素，间距 4 像素，输入宽度保证等分落在整数坐标上。

zgpui 固定为 `1d796d1fc63808dc099ed7b10c92e75835ae2814`（0.1.0）；GPUI 固定为 Zed `a246423a3b24a08e0d0c8574eab3a9de422747e0`（0.2.2）。唯一上游补丁是导出已有布局引擎的可见性修正，没有修改算法。两库位于同一个计时可执行文件中，统一 Rust 1.100.0、opt-level 3、thin LTO、一个 codegen unit。完整锁、源码、补丁和两个二进制散列见[来源收据](provenance.json)。

保留布局允许 GPUI 使用正常缓存；zgpui 当前的 `Layout::new` 会生成新的布局快照。几何查询只比较 zgpui 按钮几何与 GPUI `Bounds` 的线性宿主适配器，不包括焦点、冒泡、可访问性或平台输入事件分发。

## 验证先于计时

两份程序分别通过 20 组独立预期矩形校验，每组还执行 2,048 次确定性命中查询。最初两次失败来自夹具输入：自动宽度根节点没有填满可用宽度，随后默认 2 倍 DPI 又与预期的 1 倍不一致。修正仅明确 100% 根宽和初始化时的 1 倍缩放；预期结果、两库算法和优化参数没有调整。两个失败版本与最后通过版本的收据均已保留。

正式采样在托管云 Linux x86_64 环境完成，暴露的 CPU 型号为 Intel Xeon Platinum 8573C。提前选定最小允许逻辑 CPU 0，nice 19，随机种子 20261120；7 轮配对进程、每次 256 次预热和 5,000 次逐操作采样，共 224 个计时进程、1,120,000 个时间样本。分配统计使用独立可执行文件，32 次进程调用、32,768 次操作。没有删除长尾，没有因结果更换 CPU、改变计数或重采样。

## 实际差距

下表列出每个工作负载的 GPUI 时间除以 zgpui 时间。数值大于 1 表示该任务上 zgpui 的配对均值更低；它不是总体评分。

| 总节点数 | 新建布局 | 改尺寸 | 保留布局 | 几何查询 |
|---:|---:|---:|---:|---:|
| 3 | 14.00 | 10.63 | 1.68 | 0.89，区间跨 1 |
| 21 | 8.66 | 6.31 | 1.10，区间跨 1 | 0.78 |
| 73 | 13.20 | 5.71 | 0.79 | 0.78，区间跨 1 |
| 241 | 8.41 | 4.97 | 0.81 | 0.89 |

在最大测试场景中，新建布局 p50 为 zgpui 19.341 µs、GPUI 170.802 µs；改尺寸为 13.076 µs 与 62.770 µs。保留布局的方向相反：zgpui 13.088 µs、GPUI 10.866 µs。最大场景保留布局的配对均值比为 0.805，95% 区间为 0.760–0.854。完整结果中的区间按进程轮次重采样，既没有把相邻操作当成独立机器实验，也不是覆盖全部能力的联合置信结论。

分配指标也有不同方向。最大场景新建布局中，zgpui 每次 243 次分配、申请 23,293 字节；GPUI 每次 161 次分配、申请 1,022,700 字节。zgpui 申请字节更少，但分配调用次数更多。最大场景保留布局中，zgpui 每次 1 次分配、5,784 字节；GPUI 每次 16 次分配、1,920 字节。两种几何查询均未观察到计数线程上的分配。申请流量不是常驻内存，也不是 GPU 显存。

## 计量限制

69 个计时进程的批次线程 CPU 计数差为零。原始零值全部保留，并在报告中标为未分辨；它们不代表操作没有 CPU 成本。进程峰值 RSS 原始值为 11,904–124,296 KiB，随轮次增长，各组中位数恰好都是 67,304 KiB。收集器保留前轮样本，而进程启动、fork 和上下文开销没有被本门禁隔离，因此不能用这些中位数宣布两库内存相同。

选定 CPU 的整个观察区间记录了 348 个 steal ticks，占 2,521 个总观测 ticks 的 13.80%。Linux 文档将该字段描述为非自愿等待；它是整个 CPU 观察区间的计数，不是单次操作的 CPU 用时。[字段定义](https://docs.kernel.org/filesystems/proc.html#miscellaneous-kernel-statistics-in-proc-stat)与[计量质量文件](quality.json)支持这一限制。配对顺序和保留长尾使本次环境可审查，但不能证明云端没有干扰，更不能代表用户开发机的空闲物理核。

## 下一步边界

首要优化线索是大场景保留布局的重复工作，其次是几何查询路径。应先通过剖析定位，再在独立优化提交上复用同一预期结果、任务和设置。当前尚未修改 zgpui 生产实现，也没有可传播到下游的性能补丁。

本轮没有测到原生应用启动、真实 GPU 帧、文本塑形、字形像素、完整事件分发、Windows 或 macOS 原生性能。未来渲染对照必须让两条路径完成相同场景与像素工作；仅调用 zgpui 的 renderer 回调不能代表实际 GPU 渲染。
